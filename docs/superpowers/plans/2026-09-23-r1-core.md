# Project IRL R1 Core Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Deliver a locally runnable, persistent R1 activity workflow and minimal functional clients with explicit external integration boundaries.

**Architecture:** A native mini program and minimal operations web client call a TypeScript modular API. PostgreSQL is the target datastore; PGlite supports local runs and tests. Transactional commands write durable jobs and audit rows, while adapters handle external systems.

**Tech Stack:** TypeScript, Node.js, Fastify, PostgreSQL SQL, PGlite for local development, native WeChat miniprogram files, Node test runner.

**Spec:** `docs/superpowers/specs/2026-09-23-r1-functional-design.md`

## Global Constraints

- Activity record and server authorization are the source of truth.
- Only independently confirmed registrations count toward formation.
- Capacity includes confirmed, reconfirming, offered, and reserved seats.
- Every state-changing API uses actor context, expected version, and idempotency key.
- R1 never processes payment or claims external notification delivery.
- Missing integrations fail closed; manual creation remains usable.
- No unsolicited visual UI design.

## Review Focus

- A repeated registration request must not create a second seat.
- An expired invite or offer must not claim a seat.
- A stale event version must produce a conflict and preserve current state.
- A user must not read another event's private members or private reports.
- A delayed notification job must inspect current event version and consent before send.
