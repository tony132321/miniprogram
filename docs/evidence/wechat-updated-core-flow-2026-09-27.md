# 更新后微信开发者工具核心活动回归（2026-09-27）

环境：微信开发者工具 2.02.2609231、`wechatide` 0.3.11、仓库测试 AppID、独立本地 PGlite 目录 `.data/wechat-full-flow-20260927`、`DEV_AUTH=1` 的本机 API。活动、身份与场地均为合成测试数据；未使用正式微信身份、真人场地或真机。

1. 模拟器“发起”页设置羽毛球、深圳、公共球馆、2026-10-06 20:00–22:00、4–6 人、AA 上限 50 元、主办占一席且主办自行核实场地。实际点击“生成发布前预览”，页面取得版本 1 草稿；再实际点击“以上均已核实，最终发布”，活动详情与 HTTP 回读为 `RECRUITING`、版本 2、已确认 1 人。
2. 在“我的”页分别切换本地测试身份 `p1`、`p2`、`p3`，从同一有效邀请入口打开活动。三个访客页面都显示可报名；为自动化测试临时 mock 系统确认弹窗返回 `confirm=true`，分别实际点击“本人报名或申请”，每次随即恢复原生 `wx.showModal`。三人页面均回读 `CONFIRMED`、接受版本 2；`p1` 的 `/me/registrations` 另返回相同状态。mock 只证明确认回调后的业务路径，不证明真机弹窗手指操作。
3. 切回主办身份打开活动，页面显示已确认 4、本人为主办。实际点击“确认人数及场地可用并成局”，页面状态与主办身份 HTTP 详情均为 `CONFIRMED`、版本 2、确认人数 4。[成局后模拟器截图](wechat-updated-formation-2026-09-27.jpg)。
4. 复用同一隔离库重启本地 API，`p4`、`p5` 从邀请入口分别点击报名，均为 `CONFIRMED`，活动达到上限 6 人。`w1` 同样从邀请入口报名后为 `WAITLISTED`。`p5` 在活动页实际点击退出；本人 HTTP 报名列表读回 `CANCELLED`，活动确认人数为 5。`w1` 的站内 `WAITLIST_OFFER` 通知在本人页面与 HTTP 列表均为可操作；实际点击“主动确认补位”后，页面提示成功，通知不再可操作，本人 HTTP 报名为 `CONFIRMED`、接受版本 2，活动确认人数回到 6。[补位后模拟器截图](wechat-updated-offer-accepted-2026-09-27.jpg)。本次 `w1` 未开启外部提醒同意，通知 `external_status=CONSENT_WITHDRAWN`；不把站内结果记为微信模板消息送达。
5. 主办方从活动详情实际点击“编辑活动规则并预览变更”，发起页载入版本 2。实际输入新场馆名称并触发场地已核实开关，点击变更预览；页面返回仅“公共场馆”从“测试公共球馆”变为“测试公共球馆B”、受影响 6 人。点击最终确认变更后，页面和 HTTP 回读版本 3、已确认 0、待重新确认 6、`recruiting=false`。`p1` 打开详情时，页面可见旧／新场馆差异、确认截止及“确认新版本规则”按钮；本人报名仍是 `RECONFIRM_REQUIRED`、接受版本 2，见[确认前截图](wechat-updated-reconfirm-before-2026-09-27.jpg)。开发者工具未能稳定按无 ID 按钮选择该元素，本次通过页面运行时调用其 `reconfirm` 方法，并将系统弹窗确认结果临时 mock 为同意；随后恢复原生弹窗。本人页面与 HTTP 均回读 `CONFIRMED`、接受版本 3，其他 5 人仍待重新确认、招募仍暂停，见[确认后截图](wechat-updated-reconfirm-after-2026-09-27.jpg)。此处验证页面处理方法与服务端规则，未声称实际点击了该确认按钮或验证真机弹窗。
6. 给原有“确认新版本规则”按钮增加不改变界面的稳定元素 ID 后，微信开发者工具单文件 WXML 编译返回 `$gwx`；小程序相关测试 75/75 通过。复用同一隔离活动，`p2` 原报名仍为 `RECONFIRM_REQUIRED`、接受版本 2，模拟器能选中按钮并读到准确文案。只在点击期间 mock 系统弹窗 `confirm=true`，实际点击该按钮后立即恢复原生 API；页面显示“已确认新版本规则”，本人页面与 HTTP 报名均为 `CONFIRMED`、接受版本 3。[按钮点击后的模拟器截图](wechat-updated-reconfirm-tap-2026-09-27.jpg)。此结果补齐模拟器按钮触发证据，仍不代表真机触屏或真实弹窗操作。
7. 主办方在仍只有 2 人接受版本 3 时，实际点击“确认人数及场地可用并成局”，页面返回“真实确认人数不足”，活动保持 `RECRUITING`，招募仍暂停。随后主办、`p3`、`p4`、`w1` 逐一切换本地身份；每人页面先读回 `RECONFIRM_REQUIRED`、接受版本 2，再在临时 mock 系统确认弹窗后实际点击“确认新版本规则”，随即恢复原生弹窗。四人页面均读回 `CONFIRMED`、接受版本 3。主办活动详情及 HTTP 回读确认人数 6、待重新确认 0、`recruiting=false`。主办再次实际点击成局按钮，页面与 HTTP 均为 `CONFIRMED`、版本 3、确认人数 6、待重新确认 0、`recruiting=true`，场馆为“测试公共球馆B”，见[新版成局截图](wechat-updated-formation-v3-2026-09-27.jpg)。该测试验证了重大变更暂停招募、人数守卫及全员重确认后的成局闭环；系统确认弹窗仍是 mock。

首次打开“发起”页时工具侧返回一次 WXML 编译错误，页面运行时的当前页面元数据为空；同一 WXML 单文件随后编译成功，刷新再打开页面后 `safetyStatus=OPEN`，上述完整流程执行成功。后续切换身份后立刻调用自动化接口曾偶发 `timeout waiting for automator response`，待页面运行时稳定后重试成功。该现象目前记录为开发者工具时序问题；没有把一次工具调用成功当作业务完成。测试后停止本地 API，并保留隔离测试库供核查。

本证据覆盖更新后模拟器的发布、邀请报名、成局、满员候补、退出、主动补位、重大变更后全员重新确认及再次成局路径；正式 AppID、合法 HTTPS 域名、真机登录／扫码、真人场地与三场受控活动仍未验收。
