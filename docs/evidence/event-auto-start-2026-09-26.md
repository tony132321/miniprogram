# RQ09 / RQ13 活动按时进入进行中

原实现只有首位参与者扫码后才把已成局活动从 `CONFIRMED` 改为 `IN_PROGRESS`；没有扫码时，活动开始后仍保持已成局状态。现有确认成局事务会按活动开始时间写入持久 `EVENT_START` 任务。非重大修改沿用版本任务机制重排开始任务；旧版本、已取消、已结项活动的任务不改变状态。任务在数据库当前时间到达开始时间后才写入 `IN_PROGRESS`、关闭招募，并留下一条 `EVENT_STARTED` 审计。开始任务的到期判断和崩溃租约回收均以数据库时钟为准，避免应用时钟超前或滞后造成提前消耗、延迟开始。扫码先发生时，数据库时间到达活动开始后才转换状态，并记录相同的开始审计；后续任务只作无副作用跳过。迁移 27 为升级前仍处于已成局的活动补建任务，保留其原活动事实与版本。

先加测试并确认旧实现缺少开始任务和迁移回填；修复后本地测试覆盖无扫码开始、重复执行、非重大修改后的旧版任务、取消阻断、迁移回填及校验值。另用超前／滞后的应用时钟、崩溃租约和扫码先行复现边界问题，再验证不会提前转换或漏记审计。全量 `pnpm test` 通过 325/325，`pnpm typecheck` 和 `git diff --check` 通过。本机 PostgreSQL 18.6 新建空库 `irl_r1_test_event_start_clock_20260926`，两条独立连接池执行 `scripts/verify-postgres.ts`；迁移 1–27、100 名竞争者抢最后席位、两条时钟滞后的应用连接池并发领取开始任务均通过，输出 `eventStartCrossPool=true`，开始审计只出现一次。

微信开发者工具 `0.3.11` 通过本地开发 API 打开同一 PostgreSQL 测试库中的主办方活动；页面运行时为 `status=IN_PROGRESS`、`recruiting=false`，[模拟器截图](wechat-event-auto-start-2026-09-26.jpg)显示进行中状态且没有新增报名入口。测试仅在隔离库内把活动开始时间改到过去触发任务，不代表真实时间等待或线下活动已举办。正式环境后台进程可用性、真机与真实活动仍待验。
