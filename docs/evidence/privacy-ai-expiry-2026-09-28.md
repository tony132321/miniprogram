# Policy-driven AI input expiry: local code evidence

Migration 0064 records the approved `unneeded_draft_input` expiry per deletion request. `scheduleAiInputCleanup` requires a policy whose bytes match the completed deletion execution, an owner-approved positive `approved_days`, and `approved_trigger: DELETE_EXECUTION`; expiry starts at the earliest durable deletion marker time supplied by the journal. Legacy approved policies without this explicit trigger remain pending review and do not schedule automated AI cleanup. No production retention period or legal basis is selected by this code.

At expiry, `purgeExpiredAiInput` replaces draft and semantic answer/suggestion JSON with a redaction sentinel, replaces proposal payload and receipt JSON, revokes unfinished proposals, replaces draft and semantic alert review notes, and clears content-derived request and proposal hashes. It retains request rows and event links, numeric budget reservations, known cost amounts and cost status, plus sanitized provider evidence and hashed receipts needed for cost reconciliation. An `UNKNOWN` or `LOWER_BOUND` cost remains uncertain; the cleanup does not turn it into `KNOWN`. The outcome changes to partial cleanup and retains narrower pending reviews for request keys/links and provider cost provenance. Existing audit/idempotency copies and external provider copies remain separate pending classes.

The trigger in 0064 blocks new AI rows and content restoration after cleanup, while permitting numeric cost reconciliation. It takes a `users FOR SHARE` row lock before checking completion, matching the cleanup sweep's `users FOR UPDATE` lock so the scan and ordinary write serialize. A due scan excludes already completed schedules, preventing older rows from starving later requests. Cleanup is idempotent; each schedule is marked complete in the same transaction as its row changes and outcome receipt.

Local verification on 2026-09-28: `test/privacy-ai-expiry.test.ts` passed 3/3. The tests check no cleanup before expiry, exact deletion at expiry, a cumulative event budget of 17 fen before and after, unchanged `UNKNOWN` and `LOWER_BOUND` cost states, preserved structured provider evidence, proposal revocation, note/content removal, post-cleanup write rejection, numeric reconciliation, repeat cleanup returning zero, and a later request being serviced after an earlier completed schedule. A journal integration regression executes deletion, removes the local expiry plan to simulate a stale restored database, replays the durable marker, confirms the same expiry time, and completes the scheduled purge. Policy-trigger and policy-hash mismatch paths reject direct scheduling. `tsc --noEmit` passed after the concurrent profile module import was corrected. These tests use PGlite. A two-connection PostgreSQL race test was not run because the local environment has no `DATABASE_URL` or `psql`; production PostgreSQL lock behavior remains a deployment verification item.
