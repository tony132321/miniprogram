# T19/T20 迟到人数不足任务验证（2026-09-26）

报名截止时确认人数跌破最低值，原有后台任务会按已披露规则取消未开始活动，并生成持久站内取消消息。若任务因停机或排队延迟到活动开始后再执行，旧代码仍会把状态写成 `CANCELLED`，相当于事后正常取消。新增用例先得到实际失败：期望 `CONFIRMED`，读回却是 `CANCELLED`。

修复后任务在活动行锁下比较执行时间和活动开始时间，并在真正写入 `CANCELLED` 的 SQL 条件中再次使用数据库当前时间。即使任务入口捕获的时间早于开始、执行时已经越过开始，也不会事后取消。开始后人数仍不足时不改活动状态、不生成正常取消通知，审计一次 `SHORTFALL_AFTER_START`；详情接口继续返回 `formationRisk=true` 与实际确认人数。原先开始前的人数不足取消用例仍通过，任务重放不重复记审计。

`test/lifecycle.test.ts` 与 `test/api.test.ts` 合计 42/42 通过，含旧任务时间与数据库当前时间分叉的回归；全量 `pnpm test` 283/283、`pnpm typecheck`、`git diff --check` 通过。本地另用持久 PGlite 测试活动模拟迟到任务，读回状态 `CONFIRMED`、该审计 1 条；启动开发 API 后在微信开发者工具 0.3.11 打开活动详情，实际看到“已确认 3”和“当前确认人数不足，成局有风险”。[模拟器截图](late-shortfall-risk-simulator-2026-09-26.jpg)。

模拟执行时间、开发身份和本地数据不代表真实活动已经开始；目标环境后台任务延迟、真机展示及线下事件处置仍须独立验收。
