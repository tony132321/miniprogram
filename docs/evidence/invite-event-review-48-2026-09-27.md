# 第 48 版邀请制活动内容审核：本地验证

来源为 v3.1 开发包 T28 的 `AC-PUBLISH-MODERATION`、`AC-MODERATION-DOWN` 与 PRD RQ19 §16.1：邀请卡含活动标题、时间、场地及规则，属于可分享内容。原代码把 `INVITE` 发布设为 `NOT_REQUIRED`、立即招募；匿名 `/i/:token` 在未审时仍返回摘要。此记录只报告本地代码与合成数据，不代表真实审核供应商、真人值守或微信真机验收。

## 实施的安全状态

- 邀请制与受控公开活动发布后均为 `PENDING`、`recruiting=false`；主办方任何活动字段改动都重新进入待审。审核服务未配置时保持待审，运营人员使用现有具权人工审核队列批准或驳回。只有当前版本通过后才恢复符合时限的招募。重大变更原有的重新确认暂停不会被审批覆盖。
- 匿名邀请摘要、分享意图、报名与待定、预留/认领、候补接受与自动补位、成局/重新确认在未审时有服务端挡板。既有成员的列表标题与屏蔽列表标题显示“活动审核中”；详情只显示最后获运营批准的版本，旧库迁移活动可回退到迁移前已发布版本。没有可信旧版本时只返回无场馆、时间或规则的占位，且场地依据按可见版本筛选。成员视图保留当前数据库版本号及审核状态，并标明所展示内容的版本；主办方仍能编辑与查看审核原因。小程序已知活动 ID 可在邀请摘要 404 时继续加载成员详情。候补通知在最终外部发送前再核审核状态。
- 第 48 版迁移将仍在可批准审核窗口且 `NOT_REQUIRED` 的旧邀请活动转成待审并停止招募，保留已有版本、成员和 token，供运营按当前版本审核。已过成局确认截止或已开始、但后台生命周期任务尚未推进的旧活动不进入无法批准的队列；原成员可读历史，过期匿名 token 仍失效。
- `INVITE_REVIEW_SUBMITTED` / `INVITE_REVIEW_REJECTED` 区分邀请审核的业务事件。`ACTIVITY_PUBLISHED` 在人工批准时写入；试点 28 天复用与首个可访问版本从批准时起算，迁移前已分享的邀请保留原历史口径。

## 可复验结果

- `test/invite-moderation.test.ts` 首先观察到直通发布、旧库未隔离、成员详情封锁、公开活动待审内容泄漏及旧库临近开场等红灯；修正后覆盖人工批准、再次待审与驳回、可信旧版/无旧版的成员详情、退出、举报、非重大改动签到、屏蔽列表、事实问答和 AI 上下文的版本边界。小程序行为回归覆盖已知活动 ID 遇邀请摘要 404 后仍可打开详情及待审不可分享。上述定向组合（邀请审核、页面、屏蔽、协作、AI）**24/24 通过**；`pnpm typecheck` 与 `git diff --check` 退出码 0。全量套件由最终候选统一运行，不能用定向结果替代。
- 本机 PostgreSQL 18.6、回环 `127.0.0.1:55432`、空合成库 `irl_r1_test_invite48_20260928_g` 运行 `scripts/verify-postgres.ts` 退出码 0：迁移 **48**、两个独立连接池、100 人竞争最后一席后结果为确认 4／候补 99。脚本先以运营审核邀请活动再招募，活动多次改动后各按版本再审；原有跨池认证、截止、通知、隐私及运营工单检查输出均为 `true`。

## 尚未具备的外部证据

没有正式内容审核 provider、运营真人值守与资质核验，也未在第 48 版运行微信开发者工具模拟器或真机。旧版模拟器截图只证明当时版本，不代表本次邀请审核交互已通过。重大变更会暂停成员重新确认；若人工审核跨过确认截止或开场，当前系统不会自动沿旧规则继续，须由运营人工处置或取消，此处仍是上线前必须明确的值守流程。正式 AppID、合法 HTTPS 域名、订阅模板及三场受控真实活动仍缺失；上线预检与发布验收继续保持未通过。
