# 本人活动分页服务端有界返回与客户端并发（2026-09-30）

原 `/me/events` 虽限制每页 100 条，服务端仍为每一页把该账号所有活动取回 Node、排序并哈希，客户端再串行取齐所有页。本轮保留既有无参数 `{items}` 形状；带分页参数时先在 SQL 中按当前账号可见关系选活动，按公开可见的优先级稳定排序，仅返回 `LIMIT/OFFSET` 所需行。`OFFERED` 仍优先，待审活动的隐藏开始时间不参与排序或响应。无序快照摘要继续覆盖该账号当前可见投影；下一页快照不一致仍返回 409，防止混合不同版本。

小程序请求第一页后，以最多四个并发 worker 读取余页并按 offset 合并，沿用原页面“取齐本人列表”的接口。任何页的 409、格式错误或账号切换都丢弃整批；旧无分页元数据服务仍兼容。schema 67 增加活动主办、本人报名和有效协办关系的 actor 查找索引；最新 PostgreSQL 备份／恢复演练按 schema 67 验证。

聚焦 `/me/events`／客户端分页 **11/11**、数据库迁移 **11/11**，合计 **22/22**；`pnpm typecheck`、`git diff --check` 通过。本机 PostgreSQL 18.6 在全新合成双库上完成 schema 67 备份／恢复、业务回读与外置删除标记重放，恢复库中的主办／成员身份带参分页 HTTP 均为 200、`total=1`、快照格式有效。按用户要求未运行全量测试。

服务端为了核对快照，每页仍扫描本账号可见活动；客户端仍把全部页取齐后交给现有页面。因此这里消除了每页向 Node 返回全表和串行等待，并不证明超大账号首屏恒定耗时或总传输量下降。目标环境真实量级与 GitHub 最新提交 CI 待独立验证。
